# 容量与真人席位

想同时有 30 只 Tank 和 8 名真人，会同时撞上三个上限：客户端槽位、原版脚本数量门、幸存者队伍上限。本文说明它们各自是什么、怎么绕、绕不过的部分在哪。

## 1. 三个上限

| 上限 | 由谁决定 | 能否绕过 |
|---|---|---|
| **客户端槽位**（`MaxClients`） | L4DToolZ `sv_setmax`，上限 31（32 有崩溃风险） | 可提到 31；33 会崩客户端 |
| **原版脚本数量门** | `SessionOptions.cm_TankLimit` / 插件的 `tankrun_auto_limit` | 可改，但受槽位限制 |
| **幸存者队伍上限** | `survivor_limit` 或 `tankrun_human_seats` | 可提到 8 |

关键关系：**一只原版 Tank 占一个客户端槽位。** 所以「上限 30」不等于「能刷 30 只原版」。

## 2. 槽位预算表

分母来自 L4DToolZ 的 `sv_setmax`。假设没有旁观者、其他 Bot 或正在连接的客户端。

| 总槽位 | 其他客户端 | 预留交接 | 原版 Tank 名额 | 备注 |
|---:|---:|---:|---:|---|
| 18 | 1 | 0 | 17 | 游戏默认配置 |
| 18 | 4 | 0 | 14 | |
| 18 | 8 | 0 | 10 | 8 人默认槽位下原版最多 10 只 |
| 24 | 1 | 0 | 23 | |
| 24 | 4 | 0 | 20 | |
| 28 | 1 | 0 | 27 | |
| 28 | 4 | 0 | 24 | |
| 31 | 1 | 0 | 30 | 单人满配 |
| 31 | 4 | 0 | 27 | |
| 31 | 8 | 0 | 23 | |
| 31 | 8 | 1 | 22 | 高容量档的推荐配置 |

「预留交接」是给玩家临时入队/重连保留的槽位，由 `tankrun_human_seats` 相关逻辑计算。留着能避免重连时抢不到位置，代价是少一只 Tank。

## 3. 为什么 33 会崩

同构建 `client.dll`（SHA256 `c0a8e1e8...`）的客户端循环在 `0x1008ac14` 比较 `slot - 1` 与 `0x1f`。槽位 33 时经 `0x1008ac79` 进入 `tier0.dll!Error`，报错文本 `UpdatePlayerName with bogus slot`。

**越界检查先于普通玩家信息查询**，所以即使第 33 槽是空的，只要客户端读到的上限达到 33，定时更新遍历到该索引就会触发。

结论：服务端把 `sv_setmax` 设成 32 以上时，同构建的原版客户端会崩。**31 是实际可用上限。**

证据：`evidence/tankrun-capacity/client-slot-guard.txt`（研究仓库）、`docs/tankrun-capacity.md` 第 5–7 行。

## 4. 补位 Tank（不是原版 AI）

槽位用尽后，还可以用**服务端实体**补足数量。控制中心 v2.2.0 起内嵌了这套实现（源码 `scripting/tankrun_capacity.sp` + `tankrun_capacity/`）。

| 维度 | 原版 Tank | 补位 Tank |
|---|---|---|
| 占客户端槽位 | 是 | 否 |
| AI | 引擎原生 | 插件脚本：地图 NAV + 实体碰撞追击 |
| 命中 | 原生逐骨骼 | 盒形范围 |
| 翻越/爬梯 | 支持 | **未复刻** |
| 受伤/死亡/挥拳/投石 | 原生 | 支持，用原版模型与石头实体 |
| 被其它插件当作原版 Tank | 是 | 否 |
| 计入玩家 Tank 计数器 | 是 | 否 |

启用方式：

- 控制中心内嵌版：由统一调度自动使用（先填原版槽位，达到原版预算或 12 个游戏秒没有新原版出生后才用补位）。
- 独立 `tankrun_capacity.smx`：`tankrun_capacity_enabled 1` + `tankrun_capacity_total 30`。

**不要同时启用两者的补位。** 它们会争夺同一批生成。

## 5. 真人席位

`tankrun_human_seats.smx`：

- 默认最多 4 名幸存者；服务器有 `survivor_limit` 时沿用其值；高容量模式提升到 8。
- 空闲幸存者 Bot 会被清理。
- 真人连入优先沿用游戏完成的入队；仍在旁观且有空格时接管一个可用 Bot，或创建临时 Bot 再接管。
- 退出时按 `player_bot_replace` 的 `userid` 踢出对应补位 Bot；其余闲置 Bot 每 0.25 秒检查清理。
- 旁观玩家可聊天 `!jg` / `!join` 申请席位。
- 关闭高容量模式或卸载插件会恢复原有 `survivor_limit`。

**8 个席位目前只用服务器 Bot 验证过。八个真实 Steam 客户端同时认证与联机游玩仍需独立验证。**

## 6. 启动配置

| 场景 | 启动方式 | 说明 |
|---|---|---|
| 默认（18 槽） | 原有启动方式 | 不需要 L4DToolZ |
| 100 tick 容量测试 | `tools/start_tankrun_100tick_capacity.bat` | 启动时可选 18 / 24 / 28 / 31 |
| 30 Tank + 8 人 | `tools/start_tankrun_100tick_30tanks_8players.bat` | 31 槽 + 8 席位 + 1 交接 |
| 本地压测 | `tools/start_tankrun_local_pressure.bat` | 2 秒增量压测 |
| 正式版槽位 | 游戏目录 `start_tankrun_steam_slots.bat` | 选 18–32，回车默认 31 |
| 本地首石复测 | `tools/start_tankrun_local_firstrock.bat` | 单 Tank 脚本数量门 |

启动后确认：

1. 启动日志的 `maxplayers set to N` 与你选的一致。
2. 控制台 `sm_tank_status` 的「客户端槽位」分母等于 N。
3. 只有 `sv_setmax` **配置值**不代表实际生效，必须读回。

## 7. 实测样本

以下数字来自项目内记录的实服/本地样本，**都不是全面验证**。

| 样本 | 结果 |
|---|---|
| 31 槽、1 真人、本地压测 | 22 次原版出生相邻间隔均 2.000 游戏秒；第一只到第 30 只约 60 游戏秒；首次达 30 时为 21 原版 + 9 补位 |
| 同上，30 只固定窗口 | 26 个窗口累计 52.116 秒，99.75–100.36 tick，最大间隔 37.4 ms |
| 4 只原版、本地 listen | 20 个固定数量窗口中 16 个在 99.93–100.08 tick，1 个 101.86，3 个低值（91.23 / 87.94 / 39.19） |
| 隔离服 `c2m2_fairgrounds` | 8 席位 + 22 原版 + 8 补位同时存在，读回/追击/射线/扣血/拳伤检查通过 |
| 正式版 18 槽 | 18/18 客户端、14 只原版后生成返回 `-1`，确认槽位耗尽 |
| 正式版 18 槽、30 只轮换 | 首次达到 30/30 前为 11 原版 + 19 补位 |

低值窗口的最长时间与工坊 VPK 异步读写时间重合，**但现有样本无法证明因果**。

## 8. 调参建议

| 目标 | 做法 |
|---|---|
| 8 人 + 尽量多原版 | 31 槽，`tankrun_human_seats 1`，接受原版上限约 22–23 |
| 单人刷满原版 | 31 槽，不留多人席位，原版上限 30 |
| 追求 30 只但人数多 | 允许补位（默认行为），原版先填满剩余槽位 |
| 只想验证原版行为 | 关补位：把补位相关开关关闭或只用独立插件且 `tankrun_capacity_enabled 0` |

## 9. 未解决的问题

1. 八个**真实** Steam 客户端同时连接时的容量表现。
2. 30 只混合在场的长期稳定性（样本最长约 60 秒）。
3. 补位 Tank 在客户端的移动/动画观感。
4. 32 槽是否会崩（上游标注风险，未实测）。
5. 客户端与服务端同时扩展原生槽位可行性——现有证据表明需要双侧数据结构和网络表同步改造，**当前没有做到**。
