# 验收剧本

逐项验证控制中心在**你的服务器**上的实际行为。每个脚本都写明：前置条件、操作、通过标准、失败判据、怎么恢复。

**通用规则**

1. 一次只改一个变量。
2. 用日志判定，不靠画面猜。
3. 每次记录：地图、难度、真人数量、出生序号（userid）、当时的参数实际值。
4. 测完恢复测试前读数（`sm_tank_params` 留底）。
5. 固定其它插件、固定 tickrate、固定地图。工坊下载结束再开始。

---

## S1 · 加载与依赖

**通过**：

- `sm plugins list` 显示 `Tank Run Control Center 2.2.8`
- `sm_tank_status` 无 `警告：` 行
- 日志首行 `插件已加载 v2.2.8：注册参数 57 项`

**失败判据**：版本不是 2.2.8 / 出现 `警告：Left4DHooks 原生不可用` / 出现 `警告：tankrun 模式下脚本接口未连接`。

## S2 · 参数写入与读回

**操作**

```
sm_tank_set tankrun_auto_interval 5
sm_tank_params
sm_tank_restore tankrun_auto_interval
```

**通过**：读回 `5.0000`，恢复后回到 `2.0000`。

**这一步只验证参数层**，不验证该参数在游戏里的效果。

## S3 · 手动生成（五种方式）

**前置**：玩家离开安全区，脚本阶段开放。

**操作**：依次

```
sm_tank_spawn native
sm_tank_clear
sm_tank_spawn band
sm_tank_clear
sm_tank_spawn aim
sm_tank_clear
sm_tank_spawn near
sm_tank_clear
sm_tank_spawn script
```

**通过**：每种方式都返回生成结果，`sm_tank_status` 的 AI 数量 +1，菜单分节 8 出现该 Tank。

**记录**：每种方式的实际生成位置（距离领先玩家多远）与日志里的失败原因。

## S4 · 遮挡刷点（v2.2.8 重点）

**前置**：`tankrun_spawn_visibility 1`；两名真人，一人站开阔路段、一人站拐角；固定同一张图。

**操作**：等待自动生成，或反复 `sm_tank_spawn`。

**通过**：以 **Tank 出生瞬间**为准，没有任何存活生还者能直接看到它凭空出现。允许它出生后立刻从墙后走进视野。

**失败判据**：任一名真人直接看到 Tank 凭空出现。记录时间、地图、站位、Tank 出生坐标。

**对照**：切 `tankrun_spawn_visibility 2` 重复，应当允许在视野内出现。

**已知**：本项**尚未由玩家验证**，只在编译与遮挡算例上通过。你的记录就是首次真实数据。

---

## S5 · 满员轮换

**前置**：`tankrun_auto_limit 2`，`tankrun_rotate_oldest 1`，不主动击杀。

**操作**：等第三次生成到期。

**通过**：

1. 最早那只的 `userid` 出现在日志的「满员轮换」行；
2. 随后出现一个新 `userid` 的出生；
3. 连续两次换位都对得上。

**反向对照**：`tankrun_rotate_oldest 0` 后重复，满 2 只应**停住**，不再生成。

**失败判据**：数量停住且 `sm_tank_status` 的「剩余」槽位 > 0（说明不是槽位瓶颈）；或旧 Tank 未死亡但新 Tank 已出生。

**恢复**：把数量门与轮换开关写回原值。

---

## S6 · 客户端槽位

**前置**：用 31 槽启动器；进图后。

**通过**：

1. 启动日志 `maxplayers set to 31`；
2. `sm_tank_status` 的「客户端槽位：N/31」；
3. `sm_tank_dump` 的 `max_clients` 与启动选择一致。

**失败判据**：`sv_setmax` 配置为 31 但 `MaxClients` 仍为 18 → L4DToolZ 未生效或启动参数顺序不对。

**注意**：`sv_setmax` 只表示配置值，必须读回。

---

## S7 · 首石：三组对照（最重要）

用 `tankrun_m08_probe` 分组，每组**只生成一只新 AI Tank**。

| 组 | 控制中心设置 | 命令 |
|---|---|---|
| A 默认对照 | 首石关闭（`tankrun_firstrock_enabled 0`），投石允许 | `sm_m08_begin off` |
| B 策略对照 | 首石开启，投石允许 | `sm_m08_begin on` |
| C 超时对照 | 首石开启，投石关闭（`tankrun_rock_enabled 0`） | `sm_m08_begin fail` |

每组：同图、同站位、同难度，结束后 `sm_m08_end`。

**B 组通过标准**（同一次出生串起来）：

1. 控制中心日志出现该 Tank 的首石窗口记录；
2. 同一 Tank 的能力尝试记录；
3. 同一个 `rock` 的释放前后配对；
4. 录像/画面确认石头离手。

**C 组通过标准**：窗口超时关窗，随后出现挥击/命中记录。

**失败判据 / 需单列的情况**：

- 出现多次候选尝试；
- 穿插自然投石（无法归属）；
- `CONFIG_CHANGED` 或 `peak_ai>1`（该组作废）。

**注意 v2.2.8 的行为**：不再有「763 → 761」动作改选日志。若你看到验收文档要求这条日志，那是 v2.2.6 及更早的口径。

## S8 · 攀跳落地后的禁拳保护

**前置**：首石开启；让 Tank 从高台/落差处接近目标（历史样本用高差 +267.7 与 −167.9）。

**通过**：同一 `userid` 的日志序列应为

```
首石等待落地 → （若有拳击输入）严格首石禁拳 → 首石落地恢复 → 首石原版激活尝试 → 严格首石离手
```

且落地到离手之间**没有** `拳击命中` 造成伤害的记录。

**失败判据**：落地恢复后、离手前出现拳击伤害。记录该段日志。

---

## S9 · 拳击伤害倍率

**操作**：`sm_tank_set tankrun_claw_damage_scale 2.0`，被 Tank 打一次；改回 `1.0` 再打一次。

**通过**：两次 `player_hurt` 的伤害值约为 2:1（原版基础伤害 24 左右，受难度影响）。

**失败判据**：伤害不变或比例明显偏离。记录两次的实际伤害与难度。

---

## S10 · 投石总开关

**操作**：`tankrun_rock_enabled 0`，贴近 Tank 观察 1 分钟。

**通过**：

- 完全没有石头飞出；
- 日志出现 `投石被拦截：总开关关闭`；
- `sm_tank_status` 的「投石拦截」计数增加。

**恢复**：`tankrun_rock_enabled 1`。

---

## S11 · 投石最小间隔

**操作**：`tankrun_rock_min_delay 5`，观察两次真实投石之间的间隔。

**通过**：两次 `严格首石离手` / `投石释放后` 的时间差 ≥ 5 游戏秒；期间出现 `投石被拦截：插件最小间隔`。

**注意**：这个参数只限制插件侧的二次拦截，不改变引擎的 `z_tank_throw_interval`。

---

## S12 · 目标策略

**前置**：一只 AI Tank，两名合格幸存者，一近一远、不同方向。

**操作**：依次 `tankrun_target_mode` = `0`（原生）/ `1`（最近）/ `2`（最远），交换站位后重复。

**通过**：按时间对齐 `目标策略覆盖` 记录与 Tank 实际持续追击方向，两者一致。

**失败判据**：

- 覆盖记录出现了但 Tank 仍追原来的人；
- 没有任何覆盖记录（说明该路径没经过 `L4D2_OnChooseVictim`）。

**已知**：历史日志中 39,156 条选敌回调**全部**是默认策略、覆盖记录为 0 条。所以这项极易「看起来没效果」——先确认覆盖记录是否出现，再谈追谁。

## S13 · 预设与恢复

**操作**

```
sm_tank_preset save 1 测试
sm_tank_set tankrun_auto_interval 20
sm_tank_preset load 1
sm_tank_params
sm_tank_restore all
```

**通过**：`load` 后间隔回到保存时的值；`restore all` 后回到原始值。

**注意**：预设只包含 29 个插件参数；`restore all` 恢复的是原始值层，脚本参数不在范围内。

---

## S14 · 换图与重载

**操作**：换图；然后 `sm plugins reload tankdirector_menu`。

**通过**：

- 换图后无报错，状态清零，脚本字段重新探测成功；
- 重载后定时器与脚本开关无异常；
- 重载后已在场的 Tank 不参与 `oldest`/`newest` 轮换（日志/命令会拒绝）。

## S15 · Tick 稳定性

**前置**：Tick Telemetry 已装。

**操作**：保持游戏前台、等工坊下载结束、固定同一图；出安全区后用脚本生成间隔 5 秒，把数量门依次设 1 / 4 / 8。

**通过**：每档实际达到目标后记 20 秒，只比较数量最小/峰值**均等于该档目标**的窗口，看 `effective`、`gap_p95_upper_ms`、`gap_max_ms`。

**已知基线**：4 只时中位约 100 tick，出现过长间隔且与工坊 VPK I/O 时间重合，但**未证明因果**。8 只没有样本。

## S16 · 拳种、投石和骗石视角

在本地服用 `!tank` 配置，记录 `server.dll` 短哈希、地图、难度、人数和 tickrate。测试拳击时关闭首石优先，避免它的禁拳窗口影响对照。

1. 在未投石与投石期间各只勾选一种不同的拳，交换两个阶段的设置后复测。让幸存者分别站在距离上限内外，并加入有明显高低差的站位。检查拳种改选日志、实际动作、伤害和击退。再把其中一个阶段的拳种全部取消，确认只有该阶段禁拳。
2. 先只选双手过顶高抛，再只选下勾斜抛，最后一起勾选。将两种抛法分别设置为锁定抬手后与锁定抬手前。对照 `投石选型` 和 `原版投石帧`，核对实际抛法和锁定角度。四种抛法均应各至少得到一次真实离手样本。全部取消后应观察到投石激活被拦截。
3. 开启 `不改变视角`。在抬手期间侧移到 Tank 另一侧，在同高、幸存者站高处、幸存者站低处各做一轮。对应记录抬手前角度、离手或中断时角度、恢复期结束前后的角度及 `投石阶段结束起手` 日志。保持期内两轴应保持同一参考角；逐步恢复期间，每 tick 的角度变化应不超过 `180 × tick 间隔（秒）`。跨越 ±180° 时按最短角差计算。关闭视角锁定后用相同站位做对照。
4. 用两只 AI Tank 交错起手，并在一只投石途中清理它。另一只的抛法、锁定和拳击阶段应继续按自己的事件推进；换图或槽位复用后，新 Tank 应从未投石阶段开始。
