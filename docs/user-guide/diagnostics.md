# 诊断：日志、导出与 Tick 采样

排障时不要凭画面猜。这份文档说明三个可观测来源怎么读、能回答什么问题、不能回答什么。

## 1. 三个来源

| 来源 | 文件/命令 | 性质 |
|---|---|---|
| 控制中心日志 | `logs/tankrun_control.log` | 插件视角的决策与事件，**按插件判定**，不是原生事实 |
| 诊断快照 | `sm_tank_dump` → `logs/tankrun_control_dump.txt` | 某一时点的完整状态 |
| Tick 采样 | `tankrun_tick_telemetry` → `logs/tankrun_tick.log` | 服务端推进速率与 Tank 数量 |

三者时间基准不同：控制中心日志用 `GetGameTime()`（地图开始计时），Tick 日志按窗口写，诊断快照是快照时间。对齐时用**墙钟 + 地图名 + 回合**，不要直接相减。

## 2. 控制中心日志能回答什么

| 问题 | 看什么行 |
|---|---|
| 插件真的加载了吗 | `插件已加载 v2.2.8：注册参数 57 项` |
| 依赖齐吗 | `依赖探测（静态）：Left4DHooks=可用 SDKHooks=可用` |
| 原生禁拳装上了吗 | `严格首石拳击入口：已启用原生 CTankClaw::PrimaryAttack 拦截` |
| 生成了吗、什么方式 | `命令生成：发起者=… 方式=… 结果=…` |
| 为什么没生成 | 阶段/安全区行 + 选位失败原因 |
| 满员轮换生效吗 | `满员轮换：…` / `满员轮换补位：…` 含被处死 userid |
| 首石成功吗 | `严格首石离手：Tank#N userid=M rock=R，解除禁拳` |
| 首石为什么失败 | `严格首石超时：…` 或窗口内 `严格首石禁拳：… 入口=…` |
| 投石被谁拦了 | `投石被拦截：总开关关闭` / `投石被拦截：插件最小间隔` |
| 目标策略生效了吗 | `目标策略覆盖：Tank#N 目标 A → B（插件策略）` |
| 石头刚出手就撞墙 | `投石离手后立即碰撞：… 耗时=0.0xx 秒` |

## 3. 控制中心日志不能回答什么

| 想知道的 | 为什么日志答不了 |
|---|---|
| 原生 AI 为什么选这个目标 | 日志只记录经过 `L4D2_OnChooseVictim` 的那一次调用 |
| 拳击为什么命中/没命中 | 插件只记录 `DoSwing` 和 `OnPlayerHit` 边界，不记录 trace 几何 |
| 投石为什么被引擎拒绝 | `L4D_OnCThrowActivate` 不提供失败原因 |
| 实际帧时间/画面卡顿 | 服务端日志没有客户端帧数据 |
| 地形是否真的阻挡视线 | 日志只记插件的 trace 结果，不记命中面 |

## 4. 日志节流与遗漏

插件对高频记录做了限频，读日志时要知道：

- `目标选择 forward` 每 Tank **每秒最多一条**（`tr_rock.inc:434-437`）。
- `动作选择：… 选择投石动作` 每 Tank 每秒最多一条。
- `严格首石禁拳` 每 Tank **只记首条**（`tr_rock.inc:169-176`），后续拦截不再写。
- 调试输出受 `tankrun_debug` 控制，事件记录受 `tankrun_log_events` 控制。

因此：**日志里没有某条记录，不等于事件没发生。**

## 5. 诊断快照怎么用

`sm_tank_dump` 之后先看这四块，通常就能定位：

1. **依赖块** —— 扩展是否可用、脚本是否连接。
2. **槽位块** —— `max_clients`、已连接、空闲、保留。生成失败时优先看这里。
3. **参数块** —— 当前值 / 原始值 / 写入次数。确认「我以为设了」和「实际是」是否一致。
4. **Tank 块** —— 每只 Tank 的血量、投石/拳击统计、首石窗口状态。

**行号不可靠**（参数个数会变），按块标题定位。

历史文档里出现过「第 9、14–16 行」「第 27、28 行」这类引用，那是当时快照的行号，不要照抄。

## 6. Tick 采样怎么读

`tankrun_tick.log` 每 5 秒一行。

| 字段 | 含义 | 怎么用 |
|---|---|---|
| `effective` | 引擎设定速率 | 与你的启动配置对照 |
| 实际推进速率 | 窗口内观察到的 tick 速率 | 低于 95% 的 `effective` 视为掉速 |
| `gap_max_ms` | 最长回调间隔 | 单次卡顿的幅度 |
| `gap_p95_upper_ms` | 间隔的 p95 上界 | 持续卡顿的指标 |
| `native_tanks_min` / `native_tanks_peak` | 原生 Tank 采样范围 | 确认负载 |
| `actors` | 窗口结束时补位数量 | 区分原版与补位 |
| `total_min` / `total_peak` | 总数范围 | |
| `slow_streak` | 连续掉速窗口数 | ≥3 时看 `slow_start_*` 区间 |
| `gap_end_s` | 最长间隔结束距窗口开始的秒数 | 与工坊 I/O 时间对齐用 |

### 一条重要的读法

历史样本里出现的低值窗口（91.23 / 87.94 / 39.19 tick，最大间隔 538–4973 ms）**都与工坊 VPK 异步读写时间重合**，但：

> 时间重合不等于因果。现有样本无法证明具体阻塞函数。

写报告时要保留这个限定，不要写成「工坊导致掉速」。

## 7. 与其他日志对齐

| 要确认 | 用的日志 |
|---|---|
| 出生/死亡/回合边界 | `tankrun_spawn_v0xx.log`（生成记录器） |
| 首石归因（三组对照） | `tankrun_m08_probe.log` |
| 服务端推进是否正常 | `tankrun_tick.log` |
| 引擎自身异常 | `logs/errors_*.log` |
| 工坊加载 | `logging_system.log`（游戏侧，非仓库文件） |

对齐顺序建议：先用控制中心日志定位「哪只 Tank、什么时间、发生了什么」，再用记录器确认边界，最后用 Tick 日志排除掉速。

## 8. 排障顺序

按这个顺序走，不要跳步：

1. `sm plugins list` —— 版本对不对。
2. `sm_tank_status` —— 有没有「警告：」行。
3. `logs/tankrun_control.log` 首行 —— 是不是当前版本。
4. `严格首石拳击入口` 行 —— detour 装没装。
5. `sm exts list` —— Left4DHooks / SDKHooks 在不在。
6. `sm_tank_dump` —— 槽位与参数实况。
7. 换一张干净图复现。

具体故障对照：[故障排查](../operations/troubleshooting.md)。

## 9. 提交问题时请附上

1. `sm plugins list` 输出
2. `sm_tank_status` 输出
3. `sm_tank_dump` 生成的 `tankrun_control_dump.txt`
4. 对应时间段的 `tankrun_control.log`（截取，不要整份）
5. 服务器启动参数（tickrate、`-maxplayers`、`sv_setmax`）
6. 地图、模式、难度、真人数量、装了哪些其它插件
7. 你做了什么操作、期望看到什么、实际看到什么

**不要附**：本机绝对路径的日志链接（别人打不开）、只描述「感觉不对」而没有日志的记录。
