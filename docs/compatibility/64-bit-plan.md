# 64 位兼容计划

> ⚠ **这份文档是计划，不是研究结论，也不是实现状态。**
>
> 截至 2026-11-20：
> - 仓库内**没有任何一行 64 位代码**。
> - **没有**做过 64 位逆向。
> - **没有**验证过 64 位游戏构建是否存在。
> - 全部原生地址、偏移、签名都绑定 32 位 `server.dll`。
>
> 本文的作用是：如果将来出现 64 位构建，哪些东西会坏、按什么顺序重建、哪些工作可以复用。

---

## 1. 触发条件

本计划只在以下情况才有意义：

| 条件 | 说明 |
|---|---|
| Valve/社区发布 64 位 L4D2 服务端 | 目前**没有**证据表明存在 |
| SourceMod / Left4DHooks 提供 64 位构建 | 生态前提 |
| 客户端与服务端同时 64 位 | 只改一侧会更糟（网络表、资源数组要对齐） |

任一条不成立，本计划保持休眠。

## 2. 会失效的东西（按影响面排序）

### 2.1 立即失效

| 项 | 原因 | 影响 |
|---|---|---|
| `gamedata/tankrun_firstrock.txt` | x86 序言 + `thiscall` + 32 位地址通配 | 原生禁拳 detour 装不上，首石降级为三层保护 |
| 所有报告里的 VA | 地址空间与基址不同 | 结论需要重新绑定，不能迁移 |
| 结构体偏移（`+0x1c` 等） | 指针宽度从 4 变 8，布局重排 | 所有字段读写的语义都要重新推导 |

### 2.2 需要重建

| 项 | 工作量 | 备注 |
|---|---|---|
| `CTankClaw::PrimaryAttack` 定位 | 中 | 依赖 RTTI/虚表/调用上下文，不是字符串匹配 |
| Body 状态原语 | 小 | 逻辑极简，重建快 |
| Director 计数与数量门 | 大 | 涉及多级 limit 来源与多个消费者 |
| ZSpawn 生成链 | 大 | 自动选位的 24 块 / 18 条件要重做 |
| tankrun 模式脚本 | **不受影响** | VScript 与架构无关，脚本 SHA256 可以复用 |
| 插件业务逻辑 | **基本不受影响** | 插件用公开接口，抽象层由 SourceMod/Left4DHooks 承担 |

### 2.3 可能不受影响

| 项 | 原因 |
|---|---|
| 参数表与菜单 | 纯 SourcePawn 逻辑 |
| VScript 桥 | 走实体 + `RunScriptCode`，与架构无关 |
| 配置与预设 | 文本格式 |
| 日志格式 | 文本格式 |
| 研究结论的**行为层** | 「投石离手前已创建石头实体」这类结论大概率仍成立，但**必须重新验证** |

## 3. 重建顺序

如果触发条件成立，按这个顺序做，不要跳步：

### 阶段 0：确认基线

1. 获取 64 位 `server.dll`，记录 SHA256 与字节数。
2. 确认 SourceMod / Left4DHooks 有对应 64 位构建并提供可用 native。
3. 确认 `thiscall` 在目标平台的实际约定（x64 下统一调用约定，detour 的 `CallConv` 参数要改）。
4. 建立新的 `indexes/artifacts.json`，**旧地址全部作废**。

### 阶段 1：重新定位唯一原生依赖

只需重新做一件事：定位 `CTankClaw::PrimaryAttack`。

- 方法同 32 位：RTTI → 虚表 → 调用上下文。
- 生成新的字节签名，通配所有 64 位地址/位移。
- 在 gamedata 里新增平台段（或新建文件），**注释里写新 SHA256 与新 VA**。

**完成标准**：插件加载日志显示「已启用原生 CTankClaw::PrimaryAttack 拦截」。

### 阶段 2：验证降级路径

在还没重做任何研究之前，先确认「不依赖原生的部分」在 64 位下正常：

- 参数注册与读写
- 菜单
- VScript 桥
- 生成（`L4D2_SpawnTank` 等 native 由 Left4DHooks 承担）
- 诊断导出

**这一步能跑通，说明产品在 64 位下可用（只是首石降级）。**

### 阶段 3：重建字段与语义

按 [研究路线](../research/roadmap.md) 的顺序重做：

1. Body 状态原语（最快，先做）
2. Director 计数与数量门
3. ZSpawn 生成链
4. 拳击起拳门（`M07-01` 的 50.0 是否仍是 50.0？）
5. 投石条件链

**每一项都要重新标注 `D`/`I`/`API`/`R`/`U`，不能沿用 32 位的等级。**

### 阶段 4：重新做验收

[验收剧本](../user-guide/validation-playbook.md) 全部重跑。32 位的「已验证」不迁移。

## 4. 可以复用的东西

| 资产 | 复用程度 |
|---|---|
| tankrun 脚本审计（`D05`） | **完全复用**（VScript） |
| 脚本 SHA256 与逐分支账本 | **完全复用** |
| PC01–PC26 的参数语义映射 | 大部分复用（ConVar 名通常不变） |
| 公开 Hook 的能力边界（`interfaces.md` 第四节） | 复用，但要核对 Left4DHooks 64 位实现是否相同 |
| 行为层结论（如「三层：请求/激活/离手」） | 复用为**研究假设**，必须重新验证 |
| 产品代码结构 | 复用 |

## 5. 不能复用的东西

| 资产 | 原因 |
|---|---|
| 任何具体 VA | 地址空间不同 |
| 任何结构体偏移 | 指针宽度改变导致布局重排 |
| 字节签名 | 指令编码不同 |
| 32 位下的 `D` 级结论 | 等级绑定构建，必须重新标注 |
| 客户端槽位证据（`0x1008ac14`） | 新客户端代码要重新定位 |

## 6. 风险与未决问题

| 风险 | 说明 | 当前能做什么 |
|---|---|---|
| 生态不可用 | 没有 64 位 SourceMod/Left4DHooks，插件无法运行 | 等 |
| 只改服务端 | 客户端仍是 32 位时，网络表/资源数组不匹配 | 双侧同时 |
| 结构体偏移推断错误 | 64 位下重排后「看起来能用」但语义错 | 必须逐字段重新用指令证据确认，不能按 32 位布局平移 |
| 通配字节模式失效 | x64 编码的立即数/位移长度不同 | 重新生成模式，不沿用长度 |
| 文档腐化 | 大量文档写着 32 位地址 | 本次整理已把 32/64 分文件；重建时同步更新 |

**明确不做的事**：不在没有 64 位构建的情况下「预先适配」。没有目标的适配是猜测，会污染现有证据。

## 7. 如果要开始

建议先开一份独立文档 `docs/compatibility/64bit-findings.md`，按 [证据政策](../project/evidence-policy.md) 记录：

1. 新构建的 SHA256 与字节数；
2. 每个重新定位的入口及其证据；
3. 哪些 32 位结论被证伪；
4. 哪些保持不变。

在拿到真实构建之前，这份文档应该是空的。
