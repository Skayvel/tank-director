# 研究方法与证据等级

这份规则决定了本项目为什么读起来保守。**先接受规则，再读结论。**

原始定义在 `AGENTS.md`、`docs/method.md`、`docs/completion-criteria.md`。本文是面向读者的汇总，冲突时以原始文件为准。

## 1. 两条独立的分级

项目用两套正交的标记：**证据等级**描述「这条结论有多可靠」，**函数等级**描述「这个函数研究到哪一步」。

### 证据等级

| 标记 | 含义 | 不能推出什么 |
|---|---|---|
| `D` | 原始指令直接证实 | 不代表运行时观察到 |
| `I` | 由多条事实与前提取导 | 前提变了结论就变 |
| `API` | 接口旁证（公开源码/头文件） | 不代表原生分支经过它 |
| `R` | 运行时未验证 | —— |
| `U` | 未知 | 未知不等于不存在 |

旧的档案另有 `observed-static` / `derived-static` / `hypothesis` / `user-validated` 四种来源类型，与上述不冲突。

### 结论状态

| 状态 | 用法 |
|---|---|
| `CONFIRMED` | 当前构建的具体指令/数据直接支持某个**有限**结论。不等于观察过运行 |
| `INFERRED` | 通过类型、调用和多条事实推导，必须注明前提与替代解释 |
| `ASSUMED` | 为设计或离线场景临时采用，**不能混入原版事实** |
| `UNRESOLVED` | 证据不足，写明具体问题与下一步入口 |
| `FORMALLY_PROVEN` | 需要明确命题、模型与证明产物。**当前无** |
| `RUNTIME_VALIDATED` | 有真实运行记录并绑定版本/场景/输入。**当前为 0** |

一个函数整体 `UNRESOLVED` 时可以同时包含多条 `CONFIRMED` 的局部结论。

### 函数等级 F0–F7

| 等级 | 含义 |
|---|---|
| F0 | 候选入口/虚表指针/引用，身份或边界待确认 |
| F1 | 身份与已有档案可定位 |
| F2 | 局部静态结构已核对（ABI、输入输出、状态读写） |
| F3 | 数据与接口合同可用（条件、状态转换、副作用） |
| F4 | 声明范围内的行为模型已重建 |
| F5 | 关键依赖足够用于实现 |
| F6 | 复刻实现存在，已做静态/离线差分 |
| F7 | 该函数在声明范围内完成复刻验收 |

当前状态：100 个归档函数中 98 个为 F1；两个 Body 状态原语是 F4；其余候选 F0。**没有任何 F6/F7。**

## 2. 五条硬规则

1. **地址绑定构建。** 每个地址都与 `server.dll` SHA256 绑定。新哈希 = 新构建，旧地址作废。
2. **四种事实分开。** 观察到的字节 / 推导出的结论 / 接口旁证 / 玩家验证结果，不互相升级。
3. **绑定不是调用。** vtable 绑定 ≠ 实际实例调用；字段写入 ≠ 行为消费；局部 CFG ≠ 完整程序调用图。
4. **未观察 ≠ 不存在。** 没找到的生产者要写成「未找到」，不能写成「没有」。未解析的间接调用一律计入开放前沿。
5. **默认值不是运行值。** 注册默认、模式声明、实际读回是三件事。

另外两条操作性规则：

- **分支登记要成对。** 每个条件跳转登记两个后继；switch 登记 case 与 default；循环登记入口/退出/回边。
- **采集量不是完成度。** 函数数、分支数、证据数都只是获取进度，不给全局百分比。

## 3. 为什么不给百分比

`indexes/status.json` 里 `global_coverage_percent` 是 `null`，`coverage_denominator` 是 `observed-set-only`。

原因：**没有已知的全体分支分母。** 在「到底有多少个函数属于 Tank AI」都没确定的情况下，任何百分比都是编造的。项目改用「计数 + 开放前沿清单」表达进度。

同理，`indexes/status.json` 的 `counts` 字段只是采集计数：

| 计数 | 值（2026-11-18） | 它是什么 |
|---|---:|---|
| `evidence_records` | 143 | 去重后的证据记录 |
| `functions_with_pseudocode` | 100 | 有伪代码的函数 |
| `functions_with_dossiers` | 50 | 有完整档案的函数 |
| `catalogued_basic_blocks` | 1,603 | 目录化的基本块 |
| `catalogued_cfg_edges` | 2,463 | 块后继 |
| `observed_call_edges` | 758 | 观测到的调用边 |
| `unresolved_call_sites` | 455 | **未闭合**的调用点 |
| `semantic_branch_entries` | 99 | 人工语义分支 |
| `open_frontiers` | 14 | 模块级开放前沿 |
| `user_validated_functions` | 0 | 玩家验证过的函数 |

**这些数字增加不代表完成度上升。** 证据越多，发现的未闭合调用越多，是正常现象。

## 4. 静态优先

只有在汇编、CFG、数据流和调用关系都无法确定关键语义时，才提出**最小**动态验证问题，交给能运行游戏的人。

项目本身**不启动、不附加、不注入、不修改**游戏。玩家验证由用户完成。

这条规则的实际后果：本仓库里绝大多数行为结论都停在「静态 + 待实测」。

## 5. 复核

一次简短的独立复核即可，只查三件事（`docs/review-workflow.md`）：

1. 结论是否被所引证据、VA 和关键指令支持，是否误读 ABI/this/浮点/对象类型？
2. 是否混淆目标、Body、移动、武器、出生 NAV，或把局部顺序说成全局规则？
3. 有没有会改变实现的遗漏条件、失败/中断后继或关键未闭合依赖？

不以「审查轮数」「形式证明」「动态实验数量」当作成果。
