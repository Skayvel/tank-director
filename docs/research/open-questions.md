更细的断点清单在各模块报告里（`analysis/*/unresolved.md`、`frontier.json`）。本文是可读的汇总。

## A. 阻塞或影响产品行为

### A1. 追击导航失败的真实生产者（U02）

- **问题**：`OnStuck` 与 `OnMoveToFailure` 启动同一个计时器，但「移动失败」是从哪一层、什么条件产生的？
- **已知**：`104739d0` 可启动同一时钟。
- **缺什么**：`PathFollower` / NAV 条件到该时钟的生成路径、失败枚举、重算语义。
- **入口**：从 `1046c450` 入口，沿 `PathFollower+38` 实例向上追。

### A2. 投石离手前被中断时的清理与恢复（S3A-F08）

- **问题**：投石请求成立后、石头离手前被打断（目标消失、受伤、移动、死亡），各层状态如何清理？
- **影响**：插件的首石窗口以「真实离手」为成功判据；如果中断路径不清窗口，会出现「窗口一直开着」的错误状态。
- **入口**：`analysis/parameter-control/stage3a/` 的 frontier。

### A3. 完整目标选择路径清单

- **问题**：除普通选择器 `0x104254c0` 外，还有机枪（`0x10472b30`）、接触（`0x10473c70`）、命令（`0x10473dc0`）、事件改写等路径。它们的完整条件、优先级、互相覆盖关系？
- **影响**：决定 `tankrun_target_mode` 的真实覆盖面。当前只能声明「覆盖经过 `L4D2_OnChooseVictim` 的路径」。
- **已知**：普通选择器有约 0.3 秒节流、200 单位差值分支、独立可见性分支。

### A4. 拳击命中的真实几何与计时

- **问题**：起拳之后的 Sweep 起点、方向、形状、mask、filter 分别来自哪里？`tank_attack_range` / `tank_fist_radius` 到底有没有消费点？
- **已知**：普通起拳用固定 50.0；`tank_swing_range` 有四处读取点；`weapon+1574` 不能直接当拳距。
- **影响**：决定「拳击距离/角度可精确控制」能否作为产品能力发布。

### A5. 每 Tank 独立控制的可能性

- **问题**：引擎 ConVar 是全局的。是否存在可安全使用的每实例覆盖入口？
- **影响**：决定 M10「实例隔离」能做到什么程度。当前只提供每 Tank 的策略状态与统计。

## B. 阻塞研究闭合

### B1. 死亡的最终清理

- **已知**：死亡链到达 `f0 = 1` 的显式生命状态写入；`tank_killed` 事件生产者已恢复。
- **缺什么**：life-state 2、尸体、实体删除的完整后继。
- **为什么重要**：`tank_killed` 不能证明死因，更不能证明实体已删除。而实体是否删除直接决定槽位是否释放。

### B2. Action 生命周期与活动 Action 的事件传播

- **已知**：A1 已把「卡住通知经 NextBot 组件链 → Intention → Behavior → Action」连起；A2 已追到调度器消费返回值 3。
- **缺什么**：所有计时器写入者、死亡事件订阅者、活动 Action 的实际中转。

### B3. `AllowTakeDamage` 的具体接收者类型与 VM 提供者生命周期

- **已知**：名称 → 句柄 → 同一宿主对象 → 调用现场已连。
- **缺什么**：接收者表的前提是否在所有实例成立；VM 提供者是谁、活多久。

### B4. 每个样本的 A-B-A 归因

- **问题**：卡住样本中，参数改变后寿命从 A 变 B 再回 A，能否把具体样本归因到某条分支？
- **缺什么**：每样本的计时起点、Vision age、实际受伤结果、事件日志。
- **现状**：只能给出「参数可逆地影响寿命」这一统计层面的结论。

### B5. 引擎 ConVar 注册与运行时更新传播

- **问题**：注册后的 ConVar 变更如何传播到已缓存的读取点？是否存在只在初始化时读一次的参数？
- **影响**：决定「改参数是否需要换图/重新生成 Tank」的答案。`tank_attack_range` 的玩家观测差异可能与此有关，但没有证据。

### B6. 活动 Action 与 Body/武器的分离程度

- **已知**：目标句柄、Body 请求、路径目标、武器状态各自独立。
- **缺什么**：一个请求被拒时，其它三条是否被自动取消；Action 切换时旧请求的清理时机。

## C. 运行时与部署

### C1. 128 tick

- **现状**：全部实测在 100 tick；`indexes/status.json` 明确 `128_tick_validation: not established`。
- **要做什么**：同构建、同地图、同负载下重做首石与拳击时序样本，比较 tick 换算是否仍成立。

### C2. 八个真实 Steam 客户端

- **现状**：8 席位只用服务器 Bot 验证过。
- **要做什么**：八个真实客户端同时认证、联机游玩，记录槽位、掉线、重连。

### C3. 32 槽

- **现状**：上游标注崩溃风险；项目未实测。
- **要做什么**：在隔离服上试，确认客户端是否会崩。

### C4. 客户端画面层

- **现状**：补位 Tank 的移动/动画在客户端可能有跳步/抽搐；v1.2.0 修过一版。
- **要做什么**：客户端侧逐只录屏 + 帧时间记录。仓库现有日志没有客户端帧数据。

### C5. 原生槽位的客户端/服务端双侧扩展

- **现状**：客户端资源数组与网络表是固定大小；完整扩展需要双侧改造。
- **要做什么**：这不是当前能做到的事，只是记录方向。

### C6. Linux 服务器

- **现状**：gamedata 只有 `windows` 段，detour 不会安装，其余功能按代码推断可用。
- **要做什么**：实际在 Linux 上跑一遍，确认降级路径没有意外副作用。

## D. 公开版与内部版的差异

公开发行版不包含研究仓库中的原始证据与历史工作报告，因此以下问题**对公开读者不适用**，仅记录在此以免混淆：

| 项目 | 说明 |
|---|---|
| 历史文档的版本表述 | 内部工作报告按轮次累积，部分仍写着 v2.0.1 基线。当前事实以 [版本表](../reference/versions.md) 为准 |
| 本机绝对路径 | 内部报告的日志行号引用了作者本机路径，不随公开发行；公开文档一律使用相对路径 |
| `build/` 与 `evidence/` 的体积 | 留在内部仓库，不随公开发行 |

公开范围与排除理由见 [公开发行范围](../project/publication-scope.md)。
